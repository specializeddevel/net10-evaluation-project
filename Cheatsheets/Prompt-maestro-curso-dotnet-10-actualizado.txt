Estado funcional:

* Controller API con [ApiController] y [Route("api/[controller]")].
* GET /api/customers.
* GET /api/customers/{id}.
* POST /api/customers.
* PUT /api/customers/{id}.
* DELETE /api/customers/{id}.
* Servicio en memoria registrado actualmente como singleton.
* IDs de tipo long en todas las capas.
* POST devuelve 201 Created y Location mediante CreatedAtAction.
* PUT devuelve 200 y actualiza UpdatedAt.
* DELETE devuelve 204 si elimina y 404 si no existe.
* 404 y validaciones devuelven ProblemDetails/ValidationProblemDetails con traceId.
* OpenAPI está disponible en /openapi/v1.json.

DTOs y records:

* CreateCustomerRequest es un record posicional.
* Sus DataAnnotations deben colocarse en los parámetros del constructor primario, SIN el destino property:.
* Se aprendió que MVC usa los metadatos de los parámetros para validar records posicionales.
* UpdateCustomerRequest es un record no posicional, con propiedades required/init y DataAnnotations sobre las propiedades.
* CustomerResponse es un record de salida y su Id es long.

Mapeo manual existente en CustomerMappings:

* Customer → CustomerResponse mediante ToResponse().
* CreateCustomerRequest → Customer mediante ToModel(id, createdAt).
* UpdateCustomerRequest → Customer existente mediante ApplyTo(customer, updatedAt).

La asignación de Id, CreatedAt y UpdatedAt la controla el servidor. El consumidor no envía esos campos en CreateCustomerRequest.

Decisión arquitectónica actual:

* El servicio devuelve Customer.
* El Controller hace ToResponse().
* Esto mantiene al servicio desacoplado del contrato HTTP de salida.
* El servicio todavía recibe CreateCustomerRequest/UpdateCustomerRequest como concesión temporal para no usar firmas con muchos parámetros.
* Más adelante debe implementarse realmente CreateCustomerCommand dentro de una capa Application, porque nunca utilicé ese patrón y quiero aprenderlo.
* En ese refactor se debe explicar y practicar: Request → Command → Domain/Entity → Result/Response.

Colecciones:

* Se estudiaron List<T>, IReadOnlyCollection<T> y AsReadOnly().
* Se explicó que readonly en un field impide reasignar la referencia, pero no hace inmutable el contenido.
* Se explicó que AsReadOnly protege la estructura de la colección, no vuelve inmutables sus elementos.

DELETE utiliza la forma concisa:

public bool Delete(long id)
{
    Customer? customer = GetById(id);
    return customer is not null && _customers.Remove(customer);
}

Se explicó el cortocircuito de &&. En futuros ejercicios, preferir código C# conciso e idiomático cuando siga siendo claro. La primera vez que aparezca una sintaxis compacta nueva:

1. señalarla;
2. explicar cómo funciona;
3. mostrar, al menos una vez, la versión expandida equivalente;
4. después usar normalmente la forma idiomática.

Regla: conciso y claro, sí; conciso pero críptico, no.

Pruebas HTTP:

* Para cada prueba indicar método, URL, headers, body raw JSON y resultado esperado.
* No usar curl para bodies JSON salvo que haya un motivo concreto, porque PowerShell generó problemas de escape.
* dotnet CLI y PowerShell continúan utilizándose para build, run y tareas operativas.
